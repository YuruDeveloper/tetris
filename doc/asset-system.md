## Asset이란?

**Asset(자산)**은 게임에서 사용되는 모든 외부 리소스를 의미합니다.

### Asset의 종류

#### 그래픽 리소스
- **텍스처 (Texture)**: PNG, JPG 등 이미지 파일
- **3D 모델 (Model)**: OBJ, FBX, GLTF 등 메시 데이터
- **머티리얼 (Material)**: 쉐이더와 파라미터 조합
- **쉐이더 (Shader)**: GLSL, HLSL 등 GPU 프로그램
- **스프라이트 (Sprite)**: 2D 그래픽 이미지
- **애니메이션 (Animation)**: 골격 애니메이션, 스프라이트 애니메이션

#### 오디오 리소스
- **음악 (Music)**: MP3, OGG 등 배경 음악
- **효과음 (Sound Effect)**: WAV, OGG 짧은 사운드
- **보이스 (Voice)**: 대사, 내레이션

#### 데이터 리소스
- **레벨 데이터 (Level Data)**: 맵 구성 정보
- **설정 파일 (Config)**: JSON, XML, YAML
- **스크립트 (Script)**: Lua, Python 등
- **폰트 (Font)**: TTF, OTF 글꼴 파일

#### 기타
- **프리팹 (Prefab)**: 미리 구성된 게임 오브젝트
- **파티클 시스템 (Particle System)**: 특수 효과 설정

## Asset Manager란?

**Asset Manager(자산 관리자)**는 게임의 모든 리소스를 효율적으로 로드하고, 관리하고, 해제하는 중앙 집중식 시스템입니다.

### 필요성

게임에서 직접 파일을 로드하면 발생하는 문제들:
- **중복 로딩**: 같은 텍스처를 여러 번 메모리에 올림
- **메모리 누수**: 언제 해제해야 할지 모름
- **성능 저하**: 매번 디스크에서 읽어야 함
- **의존성 관리 어려움**: 어떤 리소스가 다른 리소스를 필요로 하는지 추적 불가

Asset Manager는 이런 문제들을 해결합니다.

## Asset Manager의 주요 기능

### 1. 리소스 로딩 (Resource Loading)

**역할**: 파일 시스템에서 리소스를 읽어 메모리에 적재

**처리 과정**:
- 파일 경로로부터 데이터 읽기
- 포맷에 맞게 파싱 (PNG → 픽셀 데이터)
- GPU 메모리로 업로드 (텍스처의 경우)
- 게임에서 사용 가능한 형태로 변환

**로딩 전략**:
- **즉시 로딩 (Immediate Loading)**: 요청 즉시 로드 (동기)
- **지연 로딩 (Lazy Loading)**: 실제 사용 시점에 로드
- **비동기 로딩 (Async Loading)**: 백그라운드 스레드에서 로드
- **사전 로딩 (Preloading)**: 게임 시작 또는 씬 전환 시 미리 로드

### 2. 캐싱 (Caching)

**역할**: 한 번 로드한 리소스를 메모리에 보관하여 재사용

**장점**:
- 동일한 리소스를 여러 오브젝트가 공유
- 디스크 I/O 횟수 감소
- 메모리 사용량 최적화
- 로딩 시간 단축

**캐시 전략**:
- **영구 캐시**: 게임 내내 유지 (UI 공통 리소스 등)
- **씬 캐시**: 현재 씬에서만 유지
- **LRU 캐시**: 사용 빈도에 따라 자동 해제

### 3. 참조 카운팅 (Reference Counting)

**역할**: 몇 개의 오브젝트가 해당 asset을 사용 중인지 추적

**동작**:
- asset 요청 시 참조 카운트 증가
- asset 해제 시 참조 카운트 감소
- 참조 카운트가 0이 되면 메모리에서 언로드

**이점**:
- 자동 메모리 관리
- 메모리 누수 방지
- 사용 중인 리소스 실수로 삭제 방지

### 4. 핸들 시스템 (Handle System)

**역할**: 직접 포인터 대신 간접 참조 방식 사용

**핸들의 장점**:
- asset이 메모리에서 이동해도 핸들은 유효
- asset 언로드 후 재로드 시 같은 핸들 사용 가능
- 잘못된 메모리 접근 방지
- 직렬화 용이 (ID만 저장)

**핸들 타입**:
- ID 기반 (uint64 등)
- 경로 기반 (string)
- GUID 기반 (Globally Unique Identifier)

### 5. 의존성 관리 (Dependency Management)

**역할**: asset 간의 의존 관계 추적

**예시**:
- 머티리얼 → 텍스처, 쉐이더에 의존
- 3D 모델 → 머티리얼에 의존
- 프리팹 → 모델, 스크립트에 의존

**처리**:
- 의존하는 asset을 먼저 로드
- 부모 asset이 언로드될 때 자식도 확인
- 순환 의존성 감지 및 경고

### 6. 핫 리로딩 (Hot Reloading)

**역할**: 게임 실행 중 파일 변경 감지 및 자동 재로드

**개발 시 이점**:
- 게임 재시작 없이 리소스 수정 가능
- 빠른 반복 개발
- 아티스트/디자이너 작업 효율 향상

**구현 방식**:
- 파일 시스템 모니터링 (inotify, FSEvents 등)
- 변경 감지 시 해당 asset만 재로드
- 사용 중인 오브젝트에 자동 반영

## 동작 원리

### 기본 플로우

```
[게임 오브젝트]
      ↓
  "texture.png 필요"
      ↓
[Asset Manager]
      ↓
   캐시 확인
      ↓
    있음? ──Yes→ [캐시된 asset 반환]
      ↓              ↓
     No           참조 카운트++
      ↓              ↓
  파일 로드        [핸들 반환]
      ↓
  파싱/변환
      ↓
  캐시 저장
      ↓
 참조 카운트 = 1
      ↓
  [핸들 반환]
```

### 언로드 플로우

```
[게임 오브젝트]
      ↓
 "asset 사용 완료"
      ↓
  Release() 호출
      ↓
[Asset Manager]
      ↓
 참조 카운트--
      ↓
  카운트 = 0?
      ↓
    Yes ──→ GPU 메모리 해제
      ↓
   캐시 제거
      ↓
   메모리 해제
```

### 비동기 로딩 플로우

```
[메인 스레드]           [로딩 스레드]
      ↓
 LoadAsync()
      ↓
  로딩 작업 큐에 추가
      ↓                       ↓
   임시 핸들 반환         큐에서 작업 꺼냄
      ↓                       ↓
  게임 계속 실행          파일 읽기
      ↓                       ↓
   (다른 작업)            파싱/변환
      ↓                       ↓
 로딩 완료 확인?           GPU 업로드 준비
      ↓                       ↓
   폴링 또는 콜백         로딩 완료 표시
      ↓                       ↓
  핸들이 유효해짐          대기 상태
```

## 디자인 패턴

### 1. Singleton Pattern

**적용**: Asset Manager는 전역적으로 하나만 존재

**이유**:
- 리소스 캐시의 일관성 유지
- 전역 접근 가능
- 중복 인스턴스로 인한 메모리 낭비 방지

**주의사항**:
- 멀티스레드 환경에서 동기화 필요
- 테스트 시 모킹 어려움

### 2. Factory Pattern

**적용**: 리소스 타입별로 적절한 로더 사용

**구조**:
- AssetManager가 각 타입별 Factory 보유
- TextureFactory, ModelFactory, AudioFactory 등
- 확장자 또는 타입 정보로 적절한 Factory 선택

**장점**:
- 새로운 리소스 타입 추가 용이
- 각 타입의 로딩 로직 분리
- 단일 책임 원칙 준수

### 3. Handle/Resource Pattern

**적용**: 직접 포인터 대신 핸들(ID) 사용

**이점**:
- 메모리 재배치 안전성
- Dangling pointer 방지
- 리소스 언로드 후 재로드 가능

**구현**:
- 핸들은 불변 ID
- Asset Manager 내부에서 ID → 실제 리소스 매핑
- 잘못된 핸들 접근 시 안전하게 처리

### 4. Observer Pattern

**적용**: Hot Reloading, 리소스 변경 감지

**구조**:
- 파일 시스템 감시자가 변경 감지
- 등록된 Observer들에게 알림
- 사용 중인 오브젝트가 자동으로 업데이트

### 5. Object Pool Pattern

**적용**: 자주 생성/삭제되는 리소스 관리

**사용 예**:
- 파티클 텍스처
- 임시 렌더 타겟
- 사운드 인스턴스

**이점**:
- 메모리 할당/해제 오버헤드 감소
- 메모리 단편화 방지

## Asset의 생명주기

### 1. 생성 단계 (Creation)

**과정**:
- 파일 시스템에서 데이터 읽기
- 메모리 할당
- 데이터 파싱 및 검증
- 플랫폼별 리소스 생성 (예: OpenGL 텍스처 객체)

**상태**: `Loading` → `Loaded`

### 2. 사용 단계 (Usage)

**특징**:
- 여러 오브젝트가 동시 참조 가능
- 읽기 전용 (일반적으로)
- 참조 카운트 증가/감소

**상태**: `Loaded`

### 3. 언로드 후보 단계 (Unload Candidate)

**조건**:
- 참조 카운트 = 0
- 일정 시간 사용되지 않음 (LRU)
- 메모리 압박 상황

**상태**: `Loaded` → `UnloadPending`

### 4. 언로드 단계 (Unloading)

**과정**:
- GPU 리소스 해제
- 메모리 해제
- 캐시에서 제거

**상태**: `UnloadPending` → `Unloaded`

### 생명주기 다이어그램

```
[Unloaded] ──Load()──→ [Loading]
                            ↓
                    파일 읽기 완료
                            ↓
                        [Loaded]
                            ↓
                    참조 카운트 > 0
                            ↓
                        (사용 중)
                            ↓
                    참조 카운트 = 0
                            ↓
                   [UnloadPending]
                            ↓
                      일정 시간 경과
                            ↓
   [Unloaded] ←──Unload()──
```

## 실제 게임 엔진에서의 활용

### Unity

**특징**:
- `Resources.Load()`: 동기 로딩
- `Addressables`: 비동기 로딩, 의존성 관리
- Asset Bundle: 압축된 리소스 패키지
- `AssetDatabase` (에디터): 개발 중 asset 관리

**장점**:
- 자동 참조 카운팅 (가비지 컬렉션)
- 씬별 자동 로딩/언로딩
- 에디터에서 실시간 프리뷰

### Unreal Engine

**특징**:
- `FStreamableManager`: 비동기 로딩
- Soft/Hard Reference: 명시적 의존성 관리
- Pak 파일: 암호화된 리소스 패키징
- 자동 LOD 관리

**장점**:
- 매우 강력한 에디터 통합
- 레벨 스트리밍 지원
- 대용량 월드 최적화

### Godot

**특징**:
- `ResourceLoader`: 동기/비동기 로딩
- `.tres` 파일: 텍스트 기반 리소스
- 씬도 하나의 리소스로 취급

**장점**:
- 가벼운 리소스 시스템
- 텍스트 포맷으로 버전 관리 용이

### 커스텀 엔진 (OpenGL/Vulkan)

**일반적인 구조**:
- 핸들 기반 시스템
- 명시적 로드/언로드
- 수동 참조 카운팅 또는 스마트 포인터
- 쉐이더, 텍스처, 메시 별도 관리

**장점**:
- 완전한 제어권
- 특정 용도 최적화 가능
- 메모리 사용량 최소화

## 최적화 전략

### 메모리 최적화

1. **스트리밍**: 큰 리소스를 부분적으로 로드
2. **압축**: CPU 시간과 메모리 절충
3. **Mipmap**: 텍스처 LOD 사용
4. **Atlas**: 작은 텍스처들을 하나로 합침

### 로딩 시간 최적화

1. **병렬 로딩**: 멀티스레드 활용
2. **우선순위 큐**: 중요한 리소스 먼저 로드
3. **백그라운드 로딩**: 게임 플레이 중 미리 로드
4. **점진적 로딩**: 필수 리소스만 먼저, 나머지는 나중에

### GPU 최적화

1. **배치 업로드**: 여러 리소스를 한 번에 GPU에 전송
2. **리소스 재사용**: 비슷한 크기의 버퍼/텍스처 재활용
3. **지연 생성**: GPU 리소스는 실제 렌더링 직전 생성

## 구현 시 고려사항

### 멀티스레딩

**문제**:
- 동시 로딩 중 캐시 충돌
- GPU 컨텍스트는 단일 스레드

**해결**:
- 파일 I/O와 파싱은 워커 스레드
- GPU 업로드는 메인 스레드에서 처리
- 캐시 접근 시 Mutex 사용

### 에러 처리

**발생 가능한 에러**:
- 파일 없음
- 잘못된 포맷
- 메모리 부족
- GPU 리소스 생성 실패

**처리 방법**:
- 기본 리소스 제공 (fallback texture)
- 로그 남기기
- 에러 상태를 핸들에 표시

### 플랫폼 차이

**고려사항**:
- 파일 경로 구분자 (/, \)
- 엔디안 (Big/Little)
- 압축 포맷 지원 여부
- 텍스처 포맷 호환성

**해결**:
- 추상화 레이어 구축
- 플랫폼별 로더 구현
- 공통 중간 포맷 사용

### 관련 개념

- **리소스 패키징**: 배포용 파일 번들링

- **모딩 지원**: 사용자 제작 리소스 로드

1. 기본 파일 I/O와 이미지 라이브러리 (stb_image 등)
2. 간단한 텍스처 로더 구현
3. 캐싱 시스템 추가
4. 참조 카운팅 구현
5. 비동기 로딩 추가
6. 다양한 리소스 타입 지원
